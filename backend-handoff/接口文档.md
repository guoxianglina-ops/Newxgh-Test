## 一、系统概述

象过河仓库管理系统（XiangGuoHe WMS）是一个前后端分离的 Web 应用。前端是纯静态 HTML + JavaScript 单页应用，后端需要提供 RESTful API 进行数据存取。

### 架构说明

```
┌──────────────┐     HTTP/JSON      ┌──────────────────┐
│  前端 (SPA)   │ ◄──────────────► │   后端 (REST API)  │
│  index.html  │                    │   数据库          │
│  mobile.html │                    │   (PostgreSQL/    │
│  wms-core.js │                    │    MySQL/任意)    │
└──────────────┘                    └──────────────────┘
```

### 模式切换

前端自动检测运行环境：
- 通过 `http://` 访问 → **API 模式**（走后端接口）
- 通过 `file://` 打开 → **本地模式**（走 localStorage，不依赖后端）

二维码中固定写入 `http://服务器地址/mobile.html?action=...`，扫码后自动打开手机版页面。

### 注意事项

> **⚠ 二维码地址一旦确定不要轻易变更。** 所有已打印贴在商品上的二维码里包含了完整的服务器地址。如果服务器地址变了，旧二维码全部报废，必须重新生成、重新打印。

## 六、API 接口

### 6.1 通用规范

- **Base URL**: `http://{服务器地址}:{端口}/api`
- **Content-Type**: `application/json`
- **认证**: HTTP Header `X-User-AccountId` 和 `X-User-Role`（当前方式，可改为 JWT）

**通用返回格式**：

```json
{ "code": 200, "message": "success", "data": {} }
```

**错误码**：

| code | 说明 |
|------|------|
| 200 | 成功 |
| 400 | 参数有误 |
| 401 | 未登录 |
| 403 | 无权限 |
| 404 | 数据不存在 |
| 409 | 版本冲突 |
| 500 | 服务器错误 |

#### POST /api/data —— 保存全部数据（乐观锁）

前端把所有数据整个 JSON 对象提交过来。使用乐观锁防止并发覆盖。

**请求体**：

```json
{
  "version": 5,
  "data": { ... }
}
```

| 字段 | 说明 |
|------|------|
| version | 客户端持有的版本号 |
| data | 完整的数据库 JSON |

**成功**：

```json
{ "code": 200, "message": "success", "data": { "version": 6 } }
```

**版本冲突**（客户端版本 ≠ 服务端版本）：

```json
{
  "code": 409,
  "message": "版本冲突，请重新拉取",
  "data": { "serverVersion": 7, "serverData": { ... } }
}
```

**逻辑**：
1. 如果 `请求version == 服务器当前version` → 写入成功，version+1
2. 如果 `请求version != 服务器当前version` → 返回 409 + 服务器最新数据，前端自动合并后重试

#### POST /api/id/allocate —— 批量分配 ID（并发安全）

**请求体**：

```json
{
  "keys": [
    { "key": "purchaseOrder", "count": 50 },
    { "key": "goods", "count": 20 }
  ]
}
```

**响应**：

```json
{
  "code": 200,
  "data": {
    "allocations": [
      { "key": "purchaseOrder", "startId": 51, "count": 50 },
      { "key": "goods", "startId": 21, "count": 20 }
    ]
  }
}
```

**说明**：使用数据库行锁/原子操作。每个客户端预取一段 ID 号段，在本地号段内自行分配。

需要 ID 分配的 key 列表：

```
goods, supplier, customer, warehouse, staff, account, unit, category,
colorGroup, sizeGroup, notification, auditLog,
purchaseOrder, purchaseIn, purchaseReturn, purchasePayment,
salesOrder, salesOut, salesReturn, salesReceipt,
checkOrder, checkProfit, checkLoss, transfer,
incomeRecord, expenseRecord,
quotation, member, memberRecharge, posOrder,
invoice, project, rental, repair, rebate,
stockFlow, completedBatch
```

### 6.3 审核接口

#### POST /api/audit/submit —— 提交审核

```json
{ "type": "purchaseOrder", "id": 1 }
```

将 `auditStatus` 从 `草稿` → `待审核`，创建红点通知给审核员。

#### POST /api/audit/approve —— 审核通过

```json
{ "type": "purchaseIn", "id": 1 }
```

**这一步需要数据库事务！** 带 ❖ 标记的单据审核通过时涉及库存/批次/流水的变更：

| 单据 | 审核通过时的副作用 |
|------|-------------------|
| purchaseIn ❖ | 增加库存 + 创建批次 + 生成 linkChain + 写 stockFlows + 更新关联采购订单 inQty |
| purchaseReturn ❖ | 扣减库存 + FIFO 消耗批次 + 追加 outRecord + 追加 linkChain + 写 stockFlows |
| salesOut ❖ | 扣减库存 + FIFO 消耗批次 + 追加 outRecord + 追加 linkChain + 写 stockFlows + 更新关联销售订单 outQty |
| salesReturn ❖ | 增加库存 + 创建新批次 + 继承 linkChain + 写 stockFlows |
| transfer ❖ | 源仓库扣减 + 目标仓库新批次(含完整链路) + 调拨出/入流水 |

#### POST /api/audit/reject —— 驳回

```json
{ "type": "purchaseOrder", "id": 1, "reason": "单价异常" }
```

#### POST /api/audit/cancel —— 取消/撤回

```json
{ "type": "purchaseOrder", "id": 1 }
```

仅 supervisor 角色可操作。

## 九、后端实现建议

### 9.1 数据库建表建议

建议使用单表 JSONB 方案（最简单，前端代码零改动）：

```sql
CREATE TABLE app_data (
  id INTEGER PRIMARY KEY DEFAULT 1,
  data JSONB NOT NULL DEFAULT '{}'::jsonb,
  version INTEGER DEFAULT 0,
  updated_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE id_counters (
  key TEXT PRIMARY KEY,
  current_value BIGINT NOT NULL DEFAULT 0
);
```

只用一张 `app_data` 表存所有数据。读取时返回整行 JSON，写入时校验 version。

如果后端想拆成独立的关系表（goods 表、orders 表等），需要额外写数据转换层。

### 9.2 技术栈推荐（按优先级）

| 技术栈 | 理由 |
|------|------|
| **Go + PostgreSQL** | 单文件部署、内存小、并发好。推荐 Gin 框架 |
| **Node.js + PostgreSQL** | 和前端语言统一，JSON 操作方便 |
| **Python + PostgreSQL** | 开发快，FastAPI 自带 Swagger 文档 |

不建议 Java/Spring Boot（太重，小系统杀鸡用牛刀）。

### 9.3 安全建议

- 前端当前密码明文（代码中硬编码 `ACCOUNTS` 对象），后端接手后应改为 bcrypt hash + JWT 认证
- 配置 HTTPS（Let's Encrypt 免费证书）
- 配置数据库备份（每天自动备份）
- 设置防火墙，只开放必要端口

### WMS_API 模块关键函数

| 函数 | 行号 | 说明 |
|------|------|------|
| `WMS_API.init(cb)` | ~778 | 启动时拉取全量数据 + 预分配 ID |
| `WMS_API.get()` | ~939 | 读取缓存数据（`GD()` 调用此函数） |

### 数据流

```
GD() / saveD() → WMS_API.get() / WMS_API.save() → fetch() → 后端 /api/data
```

`GD()` 和 `saveD()` 是全局数据读写函数，整个代码库中所有增删改查都通过这两个函数。后端只要实现了 `GET /api/data` 和 `POST /api/data`，前端就能工作。
